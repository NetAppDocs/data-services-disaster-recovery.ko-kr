= NetApp Disaster Recovery에서 복제 계획을 최적화하십시오
:hardbreaks:
:allow-uri-read: 
:icons: font
:imagesdir: ../media/use/


[role="lead"]
복제 계획은 스냅샷 빈도, 부팅 순서, 네트워크 매핑 및 장애 조치와 장애 복구의 기타 주요 세부 정보를 정의하는 재해 복구 전략의 필수 요소입니다. NetApp Disaster Recovery에서 복제 계획을 생성하기 전에 복제 계획의 작동 방식과 모범 사례를 숙지해야 합니다.



[[about-replication-plans]]
== 복제 계획 정보

단일 복제 계획으로 여러 VM, 데이터스토어 또는 네임스페이스를 보호할 수 있습니다. 재해 복구는 보호된 데이터 리소스를 호스팅하는 모든 ONTAP 볼륨에 대해 ONTAP 일관성 그룹을 생성합니다.



[[resource-planning]]
== 자원 계획

리소스를 복제 계획에 할당하기 전에 VM 또는 네임스페이스를 구성하여 확산을 최소화하십시오. 보호가 필요한 리소스는 데이터스토어의 하위 집합에 배치하고, 보호하지 않을 리소스는 다른 데이터스토어 하위 집합에 배치하십시오. 복제 계획을 생성하기 전에 리소스 그룹을 구성하려면 link:resource-group.html["리소스 그룹 만들기"]을(를) 참조하십시오.



[[test-failover]]
== 테스트 장애 조치

복제 계획을 생성할 때 고유한 테스트 장애 조치 매핑을 구성하는 옵션이 있습니다.

복제 계획의 일부로 테스트 페일오버를 수행할 계획이라면, 페일오버 테스트 중에 시작된 VM이 운영 VM에 영향을 주지 않도록 테스트 페일오버 매핑 세트를 제공해야 합니다. 이를 위해 테스트 VM에 서로 다른 IP 주소를 제공하거나, 테스트 VM의 가상 NIC를 운영 환경과 격리되어 있으면서도 동일한 IP 구성을 가진 다른 네트워크(_버블_ 또는 _테스트 네트워크_라고 함)에 매핑할 수 있습니다.



[[snapshots]]
== 스냅샷

재해 복구는 소스 및 대상 클러스터에서 동일한 수의 스냅샷을 유지합니다.  기본적으로 이 서비스는 24시간마다 스냅샷 조정 프로세스를 수행하여 소스 및 대상 클러스터의 스냅샷 수가 동일한지 확인합니다.

다음과 같은 상황에서는 소스 클러스터와 대상 클러스터 간의 스냅샷 수가 달라질 수 있습니다.

* 일부 상황에서는 재해 복구 외부의 ONTAP 작업이 볼륨에서 스냅샷을 추가하거나 제거할 수 있습니다.
+
** 소스 사이트에 누락된 스냅샷이 있는 경우, 관계에 대한 기본 SnapMirror 정책에 따라 대상 사이트의 해당 스냅샷이 삭제될 수 있습니다.
** 대상 사이트에 누락된 스냅샷이 있는 경우, 서비스는 해당 관계에 대한 기본 SnapMirror 정책에 따라 다음 예약된 스냅샷 조정 프로세스 중에 소스 사이트에서 해당 스냅샷을 삭제할 수 있습니다.


* 복제 계획의 스냅샷 보존 횟수가 감소하면 서비스는 새로 줄어든 보존 횟수를 충족하기 위해 소스 사이트와 대상 사이트에서 가장 오래된 스냅샷을 삭제하게 됩니다.


이러한 경우 재해 복구는 다음 일관성 검사 시 소스 및 대상 클러스터에서 이전 스냅샷을 제거합니다.  또는 관리자는 *작업*을 선택하여 즉시 스냅샷 정리를 수행할 수 있습니다.image:icon-horizontal-dots.png["수평 점 작업 메뉴"] 복제 계획에서 아이콘을 선택하고 *스냅샷 정리*를 선택합니다.

재해 복구는 24시간마다 스냅샷 대칭성 검사를 수행합니다.



[[platform-managed-backups]]
== 플랫폼 관리형 백업

플랫폼 관리형 백업(즉, ONTAP 관리형 스냅샷)을 사용할 계획이라면 *MirrorAll* 복제 정책을 사용하는 것이 좋습니다. 아래 표를 참조하여 다양한 SnapMirror 복제 정책의 영향과 MirrorAll이 권장되는 이유를 확인하십시오.

[cols="10,10,80"]
|===


| 정책 | 권장 사항 | 노트 


| *MirrorAll* | 권장 | SnapMirror 전송 스냅샷을 장애 조치 또는 장애 복구 작업에 사용하지 마십시오. 


| *MirrorVault* .2+| 대안 추천 .2+| 장애 조치 또는 장애 복구 중에 선택된 스냅샷이 소스 볼륨과 대상 볼륨 모두에 있는지 확인하십시오. 그렇지 않으면 "Transition to 'snapmirrored' state failed. Reason: No common snapshot found." 라는 오류가 발생합니다. SnapMirror 전송 스냅샷을 장애 조치 또는 장애 복구 작업에 사용하지 마십시오. 


| *비동기* 


| *MirrorLatest* | 권장하지 않음 | 이 정책으로 인해 대상 시스템은 장애 조치를 위한 공통 스냅샷을 사실상 하나만 보유하게 되는데, 이는 재해 복구 시나리오에 최적화되어 있지 않습니다. 
|===


[[disaster-recovery-managed-backups]]
== 재해 복구 관리형 백업

재해 복구 관리형 백업을 사용하는 경우, 재해 복구 외부에서 생성된 SnapMirror 관계에는 다음 지침이 적용됩니다:

* SnapMirror 관계는 MirrorAll, MirrorVault, MirrorLatest 및 비동기 복제 정책을 지원할 수 있습니다.
* 이러한 관계는 재해 복구 서비스에서 관리되므로 업데이트를 예약하지 마십시오.




[[application-consistent-replicas]]
== 애플리케이션 일관성 복제본

많은 VM은 Oracle이나 Microsoft SQL Server와 같은 데이터베이스 서버를 호스팅합니다.  이러한 데이터베이스 서버에는 스냅샷이 생성될 때 데이터베이스가 일관된 상태를 유지하도록 애플리케이션과 일관된 스냅샷이 필요합니다.

애플리케이션 일관성 스냅샷은 스냅샷이 생성될 때 데이터베이스가 일관된 상태임을 보장합니다.  이는 장애 조치 또는 장애 복구 작업 후에 데이터베이스를 일관된 상태로 복원할 수 있도록 보장하기 때문에 중요합니다.

데이터베이스 서버에서 관리하는 데이터는 데이터베이스 서버를 호스팅하는 VM과 동일한 데이터 저장소에 있거나 다른 데이터 저장소에 있을 수 있습니다. 다음 표는 재해 복구에서 애플리케이션 정합성 보장 스냅샷에 대해 지원되는 구성을 보여줍니다:

[cols="20,20,40a"]
|===
| 데이터 위치 | 지원됨 | 노트 


| VM과 동일한 vCenter 데이터 저장소 내 | 예  a| 
데이터베이스 서버와 데이터베이스가 모두 동일한 데이터 저장소에 있으므로 장애 조치 시 서버와 데이터가 모두 동기화됩니다.



| VM의 다른 vCenter 데이터 저장소 내에서 | 아니요  a| 
재해 복구는 데이터베이스 서버의 데이터가 다른 vCenter 데이터 저장소에 있는 경우를 식별할 수 없습니다.  서비스는 데이터를 복제할 수 없지만 데이터베이스 서버 VM은 복제할 수 있습니다.

데이터베이스 데이터를 복제할 수는 없지만, 이 서비스는 데이터베이스 서버가 VM 백업 시점에 데이터베이스가 정지되도록 모든 필수 단계를 수행하도록 보장합니다.



| 외부 데이터 소스 내에서 | 아니요  a| 
데이터가 게스트 마운트된 LUN이나 NFS 공유에 있는 경우 재해 복구는 데이터를 복제할 수 없지만 데이터베이스 서버 VM은 복제할 수 있습니다.

데이터베이스 데이터를 복제할 수는 없지만, 이 서비스는 데이터베이스 서버가 VM 백업 시점에 데이터베이스가 정지되도록 모든 필수 단계를 수행하도록 보장합니다.

|===
예약된 백업 중에 재해 복구는 데이터베이스 서버를 중지한 다음 데이터베이스 서버를 호스팅하는 VM의 스냅샷을 만듭니다.  이렇게 하면 스냅샷을 찍을 때 데이터베이스가 일관된 상태를 유지하게 됩니다.

* Windows VM의 경우, 해당 서비스는 Microsoft 볼륨 섀도 복사 서비스(VSS)를 사용하여 두 가지 데이터베이스 서버 유형과 연동합니다.
* Linux VM의 경우, 이 서비스는 일련의 스크립트를 사용하여 Oracle 서버를 백업 모드로 전환합니다.
